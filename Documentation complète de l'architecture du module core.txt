## Vue d'ensemble

Le module `src/core` est le cœur de l'application Mattermost Connect, implémentant une architecture modulaire et réutilisable basée sur les patterns suivants :

- **Architecture en couches** : API → Services → Stores → Hooks → Composants
- **State management** : Utilisation de Zustand avec immer pour une gestion d'état immutable
- **Services** : Logique métier centralisée dans des services spécialisés
- **Communication** : Système d'événements pour la communication entre modules

## Organisation des modules

```
src/core/
├── api/                 # Client API, utilitaires de requête et hooks React Query
├── services/            # Services métier encapsulant la logique business
├── store/               # Stores Zustand pour la gestion d'état globale
└── providers/           # Providers React pour l'initialisation de l'application
```

## 1. API Client et utilitaires de requête

### Client API (`api/client.ts`)

Le client API est une classe singleton qui sert d'interface unifiée pour communiquer avec l'API Mattermost.

**Caractéristiques principales :**
- Support des modes "direct" (connexion directe au serveur Mattermost) et "proxy" (via un proxy)
- Gestion automatique des tokens d'authentification
- Traitement standardisé des erreurs
- Méthodes HTTP (GET, POST, PUT, DELETE) avec typage fort

```typescript
// Structure du client API
class ApiClient {
  // Configuration du client
  configure(config: ApiClientConfig): void
  
  // Méthodes HTTP principales
  async request<T>(path: string, options?: RequestOptions): Promise<ApiResponse<T>>
  async get<T>(path: string, options?): Promise<ApiResponse<T>>
  async post<T>(path: string, body?, options?): Promise<ApiResponse<T>>
  async put<T>(path: string, body?, options?): Promise<ApiResponse<T>>
  async delete<T>(path: string, options?): Promise<ApiResponse<T>>
  
  // Méthodes utilitaires
  setToken(token: string | null): void
  getMode(): ApiMode // 'direct' | 'proxy'
  // ...
}

// Utilisation comme singleton
export const apiClient = new ApiClient();
```

### Utilitaires d'API (`api/apiUtils.ts`)

## 2. Services

Les services encapsulent la logique métier et servent d'intermédiaire entre les API et les stores.

### Architecture des services

Chaque service :
- Est implémenté comme un singleton
- Se concentre sur un domaine métier spécifique
- Est indépendant des stores (pas de dépendances circulaires)
- Inclut la validation et le formatage des données

```typescript
// Structure générale d'un service
class XXXService {
  // Méthodes publiques avec logique métier
  public doSomething(): Result { /* ... */ }
  
  // Méthodes de formatage et de validation
  public format(entity: Entity): FormattedEntity { /* ... */ }
  public validate(entity: Entity): boolean { /* ... */ }
  
  // Méthodes utilitaires privées
  private helperMethod(): void { /* ... */ }
  
  // Notification d'événements
  public notifyXXXUpdated(entity): void {
    emitEvent(EventType.XXX_UPDATED, { entity });
  }
}

// Export comme singleton
export const xxxService = new XXXService();
```

## 3. Stores (Zustand)

Les stores gèrent l'état global de l'application en utilisant Zustand avec le middleware immer pour une mise à jour immutable de l'état.

### Architecture des stores

Chaque store :
- Utilise Zustand + immer pour la gestion d'état immutable
- Inclut CommonSlice pour les fonctionnalités partagées
- Expose des actions pour manipuler l'état
- Délègue la logique métier aux services

```typescript
// Structure générale d'un store
export const useXXXStore = create<XXXState & XXXStore>()(
  subscribeWithSelector(
    immer((set, get) => {
      // Inclusion de CommonSlice
      const commonSlice = createCommonSlice<XXXState>(set);
      
      return {
        // État de CommonSlice
        ...commonSlice,
        
        // État spécifique au store
        specificState: initialValue,
        
        // Actions
        doSomething: (param: Type) => {
          // Utilisation de services
          const result = xxxService.process(param);
          
          // Mise à jour de l'état avec immer
          set((state) => {
            state.specificState = result;
            state.lastUpdated = Date.now();
          });
          
          // Émission d'événements
          emitEvent(EventType.SOMETHING_HAPPENED, { param });
        },
        
        // Getters
        getSomething: () => {
          return get().specificState;
        },
        
        // Reset
        reset: () => {
          set((state) => {
            // Réinitialisation de l'état
            state.specificState = initialValue;
            // Réinitialisation de CommonSlice
            state.isLoading = false;
            state.error = null;
            // ...
          });
        }
      };
    })
  )
);
```

### CommonSlice (`store/slices/commonSlice.ts`)

  set: (fn: (state: T) => void) => void

  // Implémentation standard des états et actions communs
});

## 4. Intégration et utilisation

### Point d'entrée central (`src/core/store/index.ts`)

Le fichier `index.ts` du dossier `store` sert de point d'entrée central pour tous les stores et fonctionnalités :

```typescript
// Imports de tous les stores
import { useAuthStore } from "./authStore";
import { useUserStore } from "./userStore";
// ...

// Réexportation de tout
export { useAuthStore } from "./authStore";
export { useUserStore, formatUserName, getUserStatus } from "./userStore";
// ...

// Fonction pour réinitialiser tous les stores
export const resetAllStores = () => {
  // Réinitialisation dans l'ordre pour gérer les dépendances
  useWsStore.getState().reset();
  useAuthStore.getState().reset();
  // ...
};

// Fonction pour créer un snapshot de l'état actuel
export const getStoresSnapshot = () => {
  return {
    auth: useAuthStore.getState(),
    user: useUserStore.getState(),
    // ...
  };
};
```

### Flux de données typique

1. **Composant UI** appelle un hook ou une action de store
2. **Store** met à jour son état et délègue la logique métier au service approprié
3. **Service** traite les données et effectue les opérations nécessaires
4. **API Client** communique avec le serveur si nécessaire
5. **Store** met à jour son état avec les résultats
6. **Composant UI** se met à jour avec les nouvelles données

### Optimisations de performance

- **Memoization** : Les getters complexes utilisent `useMemo` ou des calculs mémoïsés dans les services
- **Subscription sélective** : `subscribeWithSelector` permet de s'abonner uniquement aux parties nécessaires de l'état
- **Mise à jour immutable efficace** : `immer` permet des mises à jour immutables sans surcoût de performance

### Gestion des erreurs centralisée

Le système d'erreur centralisé permet une gestion cohérente des erreurs :

```typescript
// Dans un service ou un store
try {
  // Code qui peut échouer
} catch (error) {
  // Utilisation du handler d'erreur centralisé
  handleError(error as Error, ErrorSource.API, ErrorSeverity.WARNING, {
    additionalContext: "some context",
  });
  throw error; // Optionnel : propager l'erreur
}
```

L'erreur est alors :
1. Enregistrée dans le ErrorStore
2. Catégorisée par source et sévérité
3. Enrichie avec des métadonnées
4. Propagée via le système d'événements si nécessaire

## Résumé

L'architecture du module `src/core` suit un pattern modulaire et bien structuré :

- **Client API** : Interface unique pour communiquer avec le serveur Mattermost
- **Services** : Logique métier encapsulée et réutilisable
- **Stores** : État global géré avec Zustand et immer
- **Événements** : Communication entre modules via un système pub/sub

Cette architecture offre plusieurs avantages :
- Séparation claire des responsabilités
- Code hautement réutilisable
- Facilité de maintenance et d'évolution
- Performance optimisée
- Gestion cohérente des erreurs

En comprenant cette architecture et ses composants, vous pouvez efficacement étendre ou modifier l'application tout en maintenant sa cohérence globale.
